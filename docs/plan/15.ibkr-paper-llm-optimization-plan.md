# IBKR Paper LLM 实盘优化闭环实施方案

> 协调说明：本文晚于 `docs/plan/14.cme-nq-futures-one-shot-research-redesign-plan.md`。涉及“Mac 本机如何接入 IBKR Paper、如何去除 TradingView 主链路、如何用 1m 信号 + 5m LLM 复核 + 真实 paper fills/PnL 优化策略”时，以本文为准。本文只授权 IBKR paper-only 验证，不授权真实 live 交易。

## 1. 目标与结论

本方案把前期 TradingView webhook 方案收敛为更可审计的 IBKR Paper 主链路：

```text
IBKR real-time MNQ market data
  -> local 1m signal engine
  -> deterministic risk pre-gate
  -> 5m structured LLM review
  -> paper-only bracket order builder
  -> IBKR Paper execution
  -> fills / commissions / positions / account PnL
  -> outcome diagnosis
  -> fast-path risk-control optimizer
  -> slow-path strategy mutation validation
```

核心结论：

- TradingView 从主链路移除；最多作为人工图表观察工具，不进入审计闭环。
- IBKR Paper 是真实执行盈亏指标的来源，TradingView alert 或 OHLCV 路径标签不能替代成交回报。
- 默认交易对象是 `MNQ` 单合约 paper order，`NQ` 先作为观察或后续扩展。
- 交易信号按 `1m` 周期运行，LLM 每 `5m` 做结构化复核和优化建议。
- LLM 可以快速建议降风险调整，但不能自动增加风险、热改策略逻辑或生成 IBKR order object。
- live trading 默认永久关闭，只有未来独立 live readiness 文档和人工审批完成后才可讨论。

## 2. 不可协商边界

### 2.1 去除 TradingView 主依赖

TradingView 不再承担：

- 信号入口。
- 行情数据源。
- paper 账户。
- 成交和 PnL 账本。
- 自动执行界面。
- 策略优化主数据来源。

如果用户继续打开 TradingView 客户端，它只能作为人工图表观察和人工复盘辅助，不作为系统输入的单一事实来源。

### 2.2 IBKR Paper-only

第一版 IBKR gateway 必须强制 paper-only：

- `live_trading_enabled = false`。
- 启动时验证连接账户为 paper account。
- 如果无法确认 paper account，gateway 进入 `blocked` 或 `safe_mode`。
- 不提供 live account 下单 endpoint。
- 不允许 LLM、WebUI 或 CLI 绕过 risk gate 直接提交 broker order。

### 2.3 官方 `ibapi` 优先

核心 gateway 使用 IBKR 官方 TWS API / `ibapi`：

- 不把 `ib_insync` 作为架构前提或核心执行依赖。
- 可以在项目内封装薄 wrapper，但必须由本项目掌控 callback、状态机、重连、审计和幂等。
- gateway 与策略研究、LLM worker、WebUI 保持清晰边界。

### 2.4 MNQ 默认

第一版默认只交易：

- `symbol = MNQ`
- `secType = FUT`
- `currency = USD`
- `quantity = 1`
- `exchange` 使用 IBKR 可用的 CME 路由配置。

合约月处理可以先手工配置 `lastTradeDateOrContractMonth`，再实现受控 front-month resolver。tick size 和 point value 必须由本地配置与 IBKR `contractDetails` 双重校验。

## 3. 运行模式

### 3.1 状态分层

系统状态至少分为：

- `offline`: 没有连接 IBKR。
- `connected_readonly`: 已连接但不允许下单。
- `data_ready`: 实时行情通过 readiness。
- `paper_armed`: paper-only 下单条件通过。
- `safe_mode`: 风险或连接异常，只允许取消、flatten、观察。
- `blocked`: account/data/contract/readiness 不满足。

任何状态转换都必须写入 append-only audit event。

### 3.2 Market data readiness

没有实时 IBKR market data 时，不允许自动 IBKR Paper 下单。

必须检查：

- market data type 是否为实时，而不是 delayed/frozen。
- `bid`、`ask`、`last` 是否可用。
- spread 是否可计算。
- 行情是否 stale。
- 合约是否可交易。
- 当前是否在允许交易时段。

失败处理：

- delayed/frozen/no data：只允许 observation，不允许 paper order。
- missing bid/ask：禁止新开仓。
- stale feed：进入 safe mode。
- feed interruption：取消未触发订单；是否 flatten 由风险策略决定。

### 3.3 1m 信号层

1m signal engine 由本地 deterministic code 执行，不依赖 TradingView/Pine：

- 从 IBKR market data 构造 1m bars。
- 计算策略所需特征。
- 读取 Strategy Spec、module memory、active strategy registry。
- 输出 structured signal candidate。
- 记录 signal hash、feature snapshot hash、strategy hash。

1m 层可以高频运行，但不能每根 bar 都调用深度 LLM。

### 3.4 5m LLM 复核层

LLM 每 5 分钟定时运行一次 review cycle，但深度 review 只处理：

- 最近 5 根 1m bar 内出现的 strong signal。
- active paper position 出现失效条件。
- 刚完成的 fill/outcome。
- spread/slippage/order rejection 异常。
- 连续亏损、日内回撤、冷却时间、事件风险等异常状态。

如果没有强触发，只生成轻量 monitor summary，不调用昂贵深度复核。

## 4. LLM 输入与输出

### 4.1 允许输入

5m LLM review 可以读取：

- 最近 5 根 1m bar。
- bid/ask/last/spread。
- 1m signal features。
- 5m aggregation。
- active strategy state。
- open paper position summary。
- recent fills summary。
- realized/unrealized PnL。
- daily drawdown usage。
- event/risk context。
- strategy card。
- known failure modes。
- previous review invalidations。
- fast-path control state。

### 4.2 禁止输入

LLM prompt 不应包含：

- 完整账户号。
- API key、session 信息或连接凭据。
- live account 状态。
- 可直接复用的 broker order control 指令。
- final holdout 明细。
- 未审计新闻文本或社交媒体观点。

账户资金类信息必须脱敏成 risk budget、drawdown usage、daily loss usage 等策略需要的摘要。

### 4.3 输出 schema

LLM 输出必须是结构化 JSON。自由文本只能进入摘要字段，不能驱动系统状态。

```json
{
  "schema_version": 1,
  "action": "paper_allow",
  "confidence": "medium",
  "bull_case": {
    "evidence": [],
    "invalidation": []
  },
  "bear_case": {
    "evidence": [],
    "invalidation": []
  },
  "risk_review": {
    "key_risks": [],
    "blocked_reasons": []
  },
  "paper_plan": {
    "entry_mode": "market_or_limit",
    "stop_loss_ticks": 20,
    "take_profit_ticks": 40,
    "max_holding_minutes": 45
  },
  "fast_path_control_diff": {
    "auto_apply": false,
    "changes": []
  },
  "mutation_proposal": {
    "create": false,
    "allowed_change": null,
    "rationale": null,
    "validation_required": []
  },
  "final_summary": {
    "market_structure": "",
    "decision_reason": "",
    "next_check": "next_5m_close"
  }
}
```

允许的 `action`：

- `no_action`
- `observe`
- `paper_allow`
- `paper_block`
- `research_candidate`
- `mutation_proposal`

LLM 不允许输出 IBKR order object。订单只能由 deterministic order builder 根据 risk-approved `paper_plan` 生成。

## 5. Paper execution

### 5.1 订单类型

第一版只允许 bracket-protected paper orders：

- 入场：`MKT` 或保守 `LMT`。
- 数量：默认 `1 MNQ`。
- 子单：stop-loss 和 take-profit 必须同时存在。
- parent/child order id 必须记录。
- `max_holding_minutes` 必须存在。
- 默认 day-flat，不隔夜。

禁止：

- 裸 market order 长期持仓。
- 亏损加仓。
- 马丁。
- DCA。
- LLM 直接构造 broker order。
- 没有保护单的入场。

### 5.2 保护失败处理

如果出现以下情况，gateway 必须进入安全处理：

- parent order 已提交但 stop/take 子单创建失败。
- 子单被 IBKR reject。
- bracket 状态不一致。
- position 与本地 expected state 不一致。

默认处理：

- 取消未成交订单。
- 必要时 flatten paper position。
- 写入 incident event。
- 降级 gateway 到 safe mode。
- 阻断后续新开仓，直到人工或自动 reconciliation 通过。

### 5.3 Kill switch

必须支持：

- cancel all open paper orders。
- flatten MNQ paper position。
- disable new entries。
- mark all active strategies observe-only。
- persist incident and reason。

Kill switch 可以由 deterministic risk gate、LLM risk-reducing fast path 或人工触发。LLM 只能触发降风险方向，不能触发加风险方向。

## 6. 执行账本与指标

真实 paper 执行盈亏必须来自 IBKR 回报和本地 reconciliation，不来自路径推测。

必须记录：

- order submitted。
- order status。
- execution fill。
- fill price。
- filled quantity。
- commission。
- average fill。
- position quantity。
- realized PnL。
- unrealized PnL。
- account drawdown usage。
- slippage vs signal reference。
- time to fill。
- rejected order。
- partial fill。
- bracket child status。

策略评价指标：

- `realized_pnl`
- `unrealized_pnl`
- `net_pnl_after_commission`
- `expectancy`
- `profit_factor`
- `win_rate`
- `max_drawdown`
- `daily_loss_usage`
- `slippage_ticks`
- `order_reject_rate`
- `partial_fill_rate`
- `time_to_fill_seconds`
- `bracket_failure_count`
- `paper_allow_would_have_lost_rate`
- `llm_action_confusion_matrix`

V1 以 paper execution PnL 为主，path-quality 只能作为补充归因。

## 7. 双速优化

### 7.1 快路径

快路径允许 5m 或日内自动生效，但只能降低风险。

自动白名单：

- 暂停策略。
- 降低策略权重。
- 提高 `min_confidence`。
- 收紧 `max_spread_ticks`。
- 降低当日最大交易次数。
- 缩小交易时段。
- 将策略降级为 `observe-only`。
- 启动 safe mode。
- 触发 kill switch。

快路径目标函数优先级：

1. 生存约束：日亏损、连续亏损、保护单失败、数据 stale。
2. 执行质量：rejected order、partial fill、slippage 恶化、bracket 异常。
3. 稳定性：错误 session/regime 暴露。
4. 收益质量：expectancy、profit factor、risk-adjusted PnL。
5. 样本频率：足够样本，但不能牺牲质量。

### 7.2 慢路径

慢路径必须生成新版本并验证：

- 修改入场逻辑。
- 修改指标组合。
- 修改核心阈值范围。
- 修改止损/止盈结构。
- 新增 strategy family。
- 增加仓位。
- 放宽风险限制。
- 从 paper 推进到任何 live 形态。

慢路径流程：

```text
LLM mutation proposal
  -> new strategy version
  -> offline backtest
  -> walk-forward validation
  -> quote/tick-aware validation when available
  -> paper probation
  -> promotion or rejection
```

### 12.1 Unit tests

必须覆盖：

- paper account detection。
- live account blocking。
- contract resolver。
- tick size / point value validation。
- market data delayed/frozen/stale blocking。
- 1m bar aggregation。
- signal candidate schema。
- LLM output validation。
- fast-path diff whitelist。
- risk-increasing diff rejection。
- bracket order construction。
- child-order failure handling。
- kill switch and flatten state transitions。

### 12.2 Integration tests

可用 fake IBKR client 测试：

- reconnect。
- duplicate order status。
- partial fill。
- reject。
- commission report delay。
- out-of-order callbacks。
- position reconciliation mismatch。
- market data interruption。

真实 TWS/IB Gateway 验收：

- 连续至少 5 个交易日 paper-only 运行。

- 至少 30 个 5m review cycles。

- 0 次 unexplained duplicate order。

### 12.3 Promotion gates

进入更高风险阶段前必须满足：

- paper-only guard verified。
- market data real-time status verified。
- bracket protection verified。
- fills/PnL ledger reconciles。
- safe mode and kill switch verified。
- LLM cannot emit order object。
- fast-path cannot increase risk automatically。
- runbook exists and has been rehearsed。

## 14. 风险与处理

### 14.1 Paper 与 live 差异

IBKR Paper fills 不等同 live fills。报告必须标记：

```text
execution_environment = ibkr_paper
live_execution_claim = false
```

Paper 结果只能证明系统闭环和 paper execution behavior，不能直接证明 live profitability。

### 14.2 行情权限不足

如果没有实时 MNQ/NQ market data，系统不能自动 paper order。允许：

- offline replay。
- delayed observation。
- readiness diagnosis。

不允许：

- 将 delayed data 视为实盘验证。
- 用 TradingView 或其他非审计 UI 补足执行级数据。

### 14.3 LLM 过度优化

LLM 快速优化只允许降风险。所有加风险、改逻辑和扩大敞口必须进入慢路径验证。

### 14.4 Gateway 状态漂移

以 IBKR 回报为准，但本地必须维护 expected state 并做 reconciliation。发现差异时：

- 阻断新开仓。
- 记录 incident。
- 进入 safe mode。
- 需要 flatten 或人工确认。

## 15. 明确不做

本阶段不做：

- TradingView webhook 主链路。
- TradingView UI 自动化。
- live trading。
- 多合约自动扩仓。
- options、stocks、crypto 多资产扩展。
- 未经验证的新 strategy family 自动上线。
- LLM 直接生成或提交 IBKR order。
- 在 delayed/frozen data 上自动 paper trading。

## 16. 成功标准

本方案完成后，系统应能做到：

- 在 Mac 上连接 IBKR Paper。
- 验证 MNQ 实时行情和合约细节。
- 本地生成 1m 策略信号。
- 每 5m 运行结构化 LLM review。
- 只提交 paper-only bracket orders。
- 记录真实 IBKR paper fills、commission、position、PnL。
- 基于 execution PnL 而不是路径推测评价策略。
- LLM 可快速自动降风险。
- LLM 不可自动加风险或热改策略。
- 所有关键状态可审计、可回放、可报告。
